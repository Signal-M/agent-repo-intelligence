结论摘要

先给产品判断，再说明判断成立的边界。

一句话产品定义

面向 Agent 开发者和高级 coding-agent 用户的本地 Agent Runtime，以 Cordis 的插件组合机制，把模型、工具、会话、权限、UI 与多 Agent 能力装配成可替换、可追踪的产品。

已验证 它同时具备 Web/CLI 产品入口和框架扩展面；判断 当前更适合作为参考架构与实验平台，而不是低风险生产底座。

业务决策

内部研发场景：Prototype；共享平台：Conditional Prototype；外部客户：Watch；监管自动执行：Reject now。 技术上优先吸收事件化 Session Log、单调收紧权限和执行轨迹；Code Mode 应 A/B 验证，全组件插件化与完整多 Agent 暂缓。

它的真正差异不在“又一个 Coding Agent”

核心在于把 Agent 产品拆成可组合服务、类型化事件和可逆副作用，并以 Profile/Bundle 装配不同产品形态。这让同一 Runtime 可支撑 Web、Headless 和自定义产品，但也把配置、兼容与测试复杂度前置。

最值得借鉴的是事件事实源

“模型可见即记录”把模型上下文、审计、恢复和 UI 投影绑定到同一 Session Log，是比单纯保存聊天消息更稳健的 Agent 产品基础。

成熟度证据不足以支持生产承诺

项目明确处于 Developer Preview；仓库测试能证明实现纪律，但没有足够任务质量、生态兼容和生产采用证据。

激活优势

本地 Web UI 把首次价值从“理解框架”缩短为“配置模型并选择仓库”。Provider 配置支持热更新，凭证在界面中以 write-only / redacted 方式处理。对开发者工具而言，这条路径已经相对完整。

放弃点与失败体验

Node 与模型凭证仍是前置门槛；Preset、Profile、工具模式与权限概念叠加后，普通用户认知成本迅速上升。当前审批 UI 缺少持续授权，复杂会话也依赖用户理解执行轨迹。

Agent 设计

中心取舍：以组合性、可审计和用户控制换取更高的系统复杂度。

设计原则

模型负责选择下一步；确定性 Runtime 负责事件、工具调度、策略、审批、取消、重试和持久化。它允许高自主执行，但试图把副作用置于可审计边界内。

自主范围与停止Turn 包含多个 Step；无工具调用、终止工具、Max Tokens、取消或 Inbox 状态决定结束/续跑。支持开放式任务，但停止可靠性依赖模型输出和 Runtime 信号。已验证
Tool / SkillNative、Code、Both 三种呈现；有界并发、独占屏障、规范化结果；Skills/MCP 作为扩展。工具组合效率高，Schema 与插件质量可能扩大失败面。已验证
计划与多 Agent标准 Preset 包含 Plan、Goal、Subagent、Workflow、后台任务和 Ralph 型循环。能力完整，但未证明复杂编排相对单 Agent 的净收益。已验证
上下文与记忆Session Log 组装模型上下文；Compaction、Token Meter 和 Tool Result Pruning 管理长任务。工作记忆与会话连续性较强；长期语义记忆未确认。部分未知
人类控制与恢复allow/deny/ask、用户审批、Sandbox、Cancel、Retry；审批不可用时 fail closed。可控性优先，但 allow-once 容易产生审批疲劳。已验证
评估与可观测Trajectory 展示 Step、Tool、Token、耗时与输入输出；Telemetry 默认关闭且无内置脱敏。调试可观测性较强，任务质量评测与数据治理仍不足。部分未知

业务适配

以下不是对仓库做统一打分，而是针对不同业务责任边界给出不同决策。

决策上下文

假设一家具备研发平台和安全团队的中大型互联网公司，优先评估内部研发仓库诊断与受监督代码修改。组织规模、任务基线和成本尚未提供；试点不允许自动合并、生产发布或访问未批准凭证。

Agent Readiness Gates · 内部研发场景

  • 业务价值unknown

    任务量、人工耗时、返工和缺陷基线未提供。

    抽样两周真实任务，建立人工周期、质量和成本基线。

  • 任务 Agent 适配pass

    仓库理解、工具选择和多步执行确实需要适应性推理。

    剔除由规则和传统自动化更稳定完成的任务。

  • 数据与工具conditional

    工具体系完整，但读取、网络、进程和插件边界需要外部隔离。

    验证 allowlist、网络出口、短期凭证、幂等和取消。

  • 可验证与停止conditional

    Session Log 与 Trajectory 较强，任务级验收和回归门仍缺失。

    为每类任务定义验收器、禁止动作和停止条件。

  • 信任与控制conditional

    单调权限与 fail-closed 审批是强项，企业身份和持续授权不足。

    测量审批疲劳、拒绝正确率、回滚和人工接管。

  • 可靠性与运营conditional

    具备压缩、重试和取消，但 Developer Preview 与插件故障提高变更风险。

    冻结版本，覆盖超时、部分副作用、恢复和升级回归。

  • 经济与组织unknown

    TCO 输入和产品、评测、工具、安全、事故 RACI 未建立。

    完成三情景 TCO，并确认长期运营责任人。

Build / Buy / Borrow / Avoid

采用上游：仅做受监督研发试点；借鉴机制：优先采用 Session Log、单调权限和 Trajectory；Fork：当前不建议；确定性自动化：规则明确和高风险子任务继续优先使用。

企业就绪度结论

最高证据支持等级是“本地或单团队、隔离、受监督试点”。共享平台仍需身份、插件治理、日志导出和升级纪律；面向外部客户还缺多租户、数据治理、SLA 和责任控制层。

判断与风险

优势来自架构一致性；风险也主要来自这份一致性的复杂代价。

  • 已验证 架构骨架完整且一致

    模型、工具、会话、审批与 UI 都能映射到统一服务/事件体系。与常见“Prompt + Tool Calling”项目相比，它更接近真正的 Agent Runtime。

  • 已验证 控制面不是后补功能

    权限决策、审批结果和工具输出进入同一执行链和日志，用户控制与审计从底层设计开始，而不是只在界面加确认按钮。

  • 推断 最强楔子是 DeepSeek 优化的开放 Harness

    DeepSeek 品牌、模型适配和开源本地分发能快速吸引开发者；向 Provider-neutral、MCP、ACP、SDK 与插件生态扩展是自然路径。

  • 未知 壁垒与实际任务收益尚未建立

    没有比较性任务结果、生态留存、迁移成本或商业化证据，不能把先进设计直接解释为 moat。

  • 已验证 成熟度仍偏早

    Developer Preview、破坏性变更和无正式 Release 与代码的完整度同时存在：工程投入很大，但产品承诺仍在形成中。

最值得警惕的风险

  • 复杂度风险：全组件插件化放大依赖顺序、配置覆盖和兼容测试负担。
  • 故障半径：插件 Schema 或 Code Mode 参数错误可能污染整次请求或导致循环。
  • 默认边界：workspace-write 不等于完整隔离，网络和进程可见性仍需单独治理。
  • 隐私风险：Telemetry 默认关闭；一旦启用，原始消息、工具参数和路径可能在无内置脱敏情况下导出。
  • 产品摩擦：Preset、Profile、工具模式和审批策略对普通用户过于技术化。
  • 验证缺口：缺少任务成功率、干预率、成本和多 Agent 增益的公开基线。

推断 缓解顺序应是：插件隔离与 Schema 校验 → 权限可解释 UX → 任务评测集 → 生态扩展。

借鉴与方案

按用户价值、战略匹配、依赖、风险和最小验证成本排序。

  1. 事件溯源式模型上下文

    把模型可见内容、工具结果、审批和恢复统一在事件日志中。依赖稳定事件词汇、投影与迁移。

    最小实验

    完整记录一个 Turn，并从日志重建一致的下一次模型请求。

    adopt
  2. 单调收紧的工具权限门

    后续策略只能保持或收紧权限，避免宽松插件覆盖拒绝。风险是审批疲劳。

    最小实验

    先门控写文件和 Shell，测拦截率、拒绝率与任务完成率。

    adopt
  3. Code Mode 多工具组合

    可能减少模型往返和成本，但需要强类型工具、规范输出与受限代码运行时。

    最小实验

    30 个任务与 Native Tool Calling A/B，比较完成率、往返、成本和恢复。

    prototype
  4. Agent Preset 能力产品包

    把角色、工具、权限和工作流打包，降低逐项配置；需要版本迁移与兼容校验。

    最小实验

    只做研究/编码两个官方预设，比较首次成功时间和配置放弃率。

    prototype
  5. 全组件插件化与完整多 Agent

    生态潜力大，但平台复杂度很可能早于用户价值，当前先开放少数稳定边界。

    观察信号

    第三方升级兼容率、插件复用量，以及多 Agent 相对单 Agent 的净收益。

    watch

最小可信闭环

目标：完成本地仓库诊断与小型重构。仅保留一个模型、事件日志、文件读写/搜索/Shell、workspace 沙箱、审批门、取消/重试、基础压缩与轨迹。用 20–30 个真实任务测完成率、干预率、拒绝正确率、恢复一致性、成本与延迟。

MVP 不做清单

不做插件市场、任意 Provider、完整 Profile DSL、多 Agent 编排、Ralph 循环、长期语义记忆和第三方 UI 插件。先证明单 Agent 的可信任务闭环，再扩展平台面。

试点与上线

目标不是证明 Harness 能运行，而是证明它在受控研发任务中比当前流程更有价值。

首个试点

内部研发 Coding Agent · Offline → Shadow。 只允许隔离仓库、测试环境和可回滚分支；禁止自动合并、生产发布、外部客户数据和未批准凭证。先证明质量、控制和恢复，再开放执行权限。

晋级条件

  • 相对人工基线获得可观测的周期或质量收益。
  • 严重错误和策略违规低于明确失败预算。
  • 取消、回滚、接管、恢复和日志重放达到约定门槛。
  • 人工审核与总成本没有抵消业务价值。
  • 产品、评测、工具、安全和事故责任人确认。

Kill Criteria

  • 发生未阻断的禁止、越权或不可逆动作。
  • 数据暴露、严重错误或成本超出预算。
  • 人工审核和返工使净价值为负。
  • 真实任务分布与评测集显著偏离。
  • 升级或插件变化使基线失效，或无法取得完整日志与回滚。
经济性状态

未知 当前不输出虚构 ROI。需要任务量、可自动化比例、节省时间、人力、模型/工具成本、审核负担、固定投入和错误损失后，运行 downside/base/upside TCO，并计算最大审核时间与最低采用率等 break-even 条件。
